最近使用 Hermes 时，遇到了一个很直接的问题：**在原来的会话里发出指令后，页面一直卡着，等了很久没有回复，最后提示 timeout。** 重新发送也没能正常继续。

后来我尝试在会话中切换模型，再发送检测指令，界面又出现红色提示：**模型服务商错误：Connection error.** 到这里，问题已经不只是“回复慢”，而是这个会话没法正常完成请求了。

我随后新开了一个排查任务，检查原会话的请求记录、模型连接以及上下文压缩状态。

本文记录这次排故过程，包括中途误判、实际采取的处理，以及最终还没有验证清楚的部分。

## 一、发现问题：发出指令后一直卡住，最后报错

实际操作过程是：

1. 在原来的会话输入指令并发送。
2. 等待很久没有正常回复，看起来像是卡住了。
3. 随后出现超时提示；查看失败记录，能看到 `APITimeoutError` 或 `APIConnectionError`。
4. 尝试切换模型并发送检测指令后，界面提示“模型服务商错误：Connection error.”

![Hermes 会话出现模型服务商连接错误的截图](/assets/hermes-context-compression/provider-connection-error.png)

*故障现场：发送检测指令后，页面提示模型服务商连接错误。*

错误详情记录如下：

```yaml
time: 2026-11-04T13:40:39.970Z
layer: provider
code: timeout
retryable: true
provider: openai-codex
model: gpt-6.1-sol
error: Connection error.
```

其中 `time` 以 UTC 记录；`layer: provider` 表示错误发生在模型服务商调用层，`code: timeout` 是超时分类，`retryable: true` 表示被标记为可重试，界面展示的错误信息则是 `Connection error.`。这条记录使用的提供商是 `openai-codex`、模型是 `gpt-6.1-sol`；不能仅根据界面上的切换提示，认定这次失败请求已经使用了其他模型。

**这条详情证实了该次请求发生超时或连接错误，但没有给出代理、网络、服务端或压缩机制中哪一项是根因。** 记录中的时间也不能直接视为所有失败请求发生的时间。

截图中还提到了代理环境变量、模型名称变更，以及旧会话绑定模型的问题。这些是当时会话里的排查描述，涉及不同的请求和任务；**不能只凭截图就认定其中某一项是本次长会话卡住的根因**，需要结合对应请求日志分别确认。

原会话已经积累了大量对话、工具调用和工具结果，因此接下来检查失败请求的大小，以及上下文压缩有没有正常工作。

排查任务检查了 10 个失败请求的转储，发现请求内容在增长：

| 观察项 | 较早的失败请求 | 较晚的失败请求 |
| --- | --- | --- |
| 消息条数 | 约 321 条 | 约 433 条 |
| 请求文本 | 约 40.5 万字符 | 约 52.5 万字符 |
| 结果 | 请求超时 | 超时或连接失败 |

这些记录都是失败样本。**它们能说明请求越来越大、调用失败，但不能单独证明请求大小就是超时的唯一原因。**

排查任务本身也遇到了类似问题：主模型连接超时后切换到备用模型，部分辅助请求经过重试才继续，一轮排查耗时约 29 分钟。

## 二、定位问题：先看压缩阈值，再看会话状态

上下文压缩的作用，是将较早的对话和工具结果整理成摘要，减少后续请求携带的历史内容。因此排查从两个问题开始：**什么时候应该触发压缩？这个会话是否真的执行成功过压缩？**

### 1. 原来的阈值是多少？

当时配置使用 `threshold: 0.3`。根据任务记录中的模型上下文窗口 272,000 Token，按 30% 计算，理论阈值约为 **81,600 Token**。

排查时还检查了可能提高阈值的 `autoraise` 机制。针对当时使用的目标模型，任务对实际代码的测试结果是没有命中该机制，因此不能直接把问题归咎于它覆盖了 30% 的阈值。

任务也曾按字符数估算最后一个请求约为 14.6 万 Token，但**这是粗略估算，不是模型实际统计结果**，不能只凭这个数字认定真实压缩触发条件一定满足。

### 2. 排除“压缩冷却把会话锁死”的猜测

排查初期，Hermes 怀疑摘要请求超时后进入冷却，导致后续自动压缩一直被跳过。但继续检查后发现：

- 压缩器对摘要输入存在裁剪，并不是简单地把完整请求原样再次发送。
- 原会话保存的状态中，没有看到压缩失败错误或冷却标记；失败计数相关字段也为 0。
- 因此，之前“摘要超时、冷却锁死会话”的说法缺少证据，排查任务后来撤回了这个结论。

**到这一步仍无法确认自动压缩没有成功的具体根因。** 没有失败标记也不能证明压缩从未尝试过，更不能排除网络、进程生命周期或其他触发条件的影响。

### 3. 会话有没有丢？

一开始在会话列表里没有找到原会话，排查任务误以为数据可能已经丢失。后来直接查询会话状态，确认会话和消息记录仍然存在，结束原因记录为 `ws_orphan_reap`，即 WebSocket 连接断开后运行中的会话被回收。

这说明**会话记录还在**；但 WebSocket 被回收并不能单独证明它就是请求超时或压缩未成功的根因。

## 三、如何处理：先降低触发上限，再分离摘要模型

根因没有完全确认，所以这里采取的是降低风险的配置调整，而不是宣称已经修复源码 Bug。

### 1. 提前尝试压缩

给压缩配置增加绝对阈值：

```yaml
compression:
  threshold: 0.3
  threshold_tokens: 60000
```

排查任务记录显示，调整后通过配置读取和压缩器的阈值计算检查，结果从约 81,600 降为 60,000 Token。这样做是希望在上下文继续膨胀前更早尝试压缩。

这个数值是针对当时环境的止血配置，不是通用最佳值。模型窗口、请求开销、网络与实际任务内容不同，需要结合实际情况调整。

### 2. 给摘要配置单独的模型

之前摘要模型使用自动选择；后续将压缩专用辅助模型设为 DeepSeek，并选择 `deepseek-v4-flash`。这样摘要与主模型可以分别配置，避免只能依赖同一条请求路径。

最初的模型连通测试只返回了 `ok`，还不足以证明完整会话压缩成功。后来查看运行日志，才确认原会话确实自动触发并完成了压缩：

| 本地时间 | 日志记录 |
| --- | --- |
| 22:51:22 | 原会话约 62,070 Token，超过 60,000 的阈值，开始自动压缩 |
| 22:52:34 | 压缩完成并提交摘要，消息由 58 条压缩为 11 条，预估约 50,239 Token |
| 22:52:42—22:53:55 | 请求再次达到阈值后又触发一次自动压缩，并成功提交 |

首次压缩从开始到完成约 72 秒，其中生成摘要约 51 秒；等待期间用户仍可能感觉界面卡住。**这证明调整后这两次自动压缩成功，并不代表之前的失败根因已经查明，也不能保证以后每次都成功。**

> 使用独立服务生成摘要意味着相关会话内容可能发送给该服务，配置前应先确认数据敏感性、服务条款、成本和可用性。

### 3. ChatGPT 明明登录过，为什么还是连接失败？

排查时分别检查了 Hermes 的 `openai-codex` 登录状态和 Codex 登录状态，二者都显示已登录。因此，当时没有证据表明必须重新登录；登录状态存在，也不代表模型请求一定能通过网络。

接着分别测试网络路径：

| 检查 | 当时的结果 |
| --- | --- |
| 直连 ChatGPT | 连接 5 秒后超时 |
| 通过本机 7890 代理访问 | 收到了 HTTP 403 响应，说明该次请求有响应，但并未成功通过服务验证 |
| Hermes 桌面后台进程 | 未看到 HTTP / HTTPS 代理环境变量 |

综合这些现象，**Hermes 没有正确使用代理是一项值得优先验证的可能原因**，但当前证据还不能证明它就是全部原因。403 也不等于模型接口调用成功，可能还涉及代理出口、访问限制或其他网络条件。

当时 Hermes 仍有任务运行，因此没有重启应用或改动登录凭据。下一步是在任务结束后，让桌面进程使用正确的代理配置启动，再实际发送一条短消息验证模型请求；如果仍然失败，再根据新日志区分网络与认证问题。

## 四、最后处理到什么程度？

| 项目 | 结果 |
| --- | --- |
| 原会话数据 | 查询到会话与消息记录，数据仍在 |
| 压缩阈值 | 已设置为 60,000 Token，配置及阈值计算已检查 |
| 摘要模型 | 已单独配置，原会话两次自动压缩并提交摘要 |
| ChatGPT 登录 | Hermes 和 Codex 均显示已登录；未重置凭据 |
| 模型连接 | 直连超时，代理路径收到 HTTP 403；尚未验证模型调用恢复 |
| 根本原因 | 历史故障根因尚未确认，不能认定 Bug 已经彻底修复 |

自动压缩已有实际成功记录；下一步重点是验证 Hermes 桌面进程的代理配置以及 ChatGPT 模型能否正常回复，并继续记录后续压缩是否稳定。

## 五、Bug 上报：应当提供什么？

这次问题适合整理为一份上游 Bug 报告，重点是：**长会话请求反复超时，同时用户无法明确看到自动压缩是否触发、跳过原因和失败阶段。**

建议上报时附上：

1. Hermes 版本、运行环境、模型及压缩配置，移除密钥和本地敏感信息。
2. 可复现的步骤：如何创建长会话、触发请求、观察超时与压缩状态。
3. 预期结果：达到实际有效阈值后，可以看到压缩触发、跳过或失败的明确状态。
4. 实际结果：请求超时、样本中未观察到成功压缩，以及连接断开后的会话状态。
5. 脱敏后的时间线、真实 Token 用量、压缩日志和错误记录；无法复现的部分明确注明。

**上报状态：**目前查阅到的任务记录里没有找到官方 Issue 链接或提交成功的凭据，因此这里不能写成“已经向官方上报”。本地排查路径已整理为一个调试技能，便于后续复查，但这不等于向上游提交 Bug。

## 六、后续预防

- 在会话还没特别长时，关注上下文占用，必要时开启新会话并保留关键任务摘要。
- 给压缩过程增加可观察信息：有效阈值、是否触发、跳过原因、摘要调用结果和耗时。
- 分开记录主请求、摘要请求和其他辅助请求的超时与重试，避免把不同故障混成一个原因。
- 修改配置后使用真实长会话验证，并保留调整前后结果，确认改善是否可重复。

这次最大的教训是：**排故过程中能很快提出一个看似合理的原因，但真正可靠的是能被日志和复现过程支持的结论。**
