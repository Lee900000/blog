2026 年 11 月 11 日下午，本地 Docker Desktop 突然退出，弹窗显示 `no space left on device`。第一反应是 Docker 的数据盘满了，但 Docker 的虚拟磁盘早已搬到外置盘 AiCode，外置盘当时还有 822 GiB 可用。

真正写满的是 Mac 内置盘。多个 Agent 的运行数据、缓存和备份，加上项目文件以及一次 Docker 迁移留下的旧备份，长期占据了有限的内置存储。Docker 仍然要在内置盘写日志，最终因日志写入失败而退出。

这是一场**存储容量管理事故**：Docker 是最先暴露问题的受影响服务。排查确认了多个大目录和旧备份的占用，但没有找到把剩余空间耗尽的最后一个写入者，也没有证明每个大目录都由 Agent 自动生成。

## 一、故障现场：Docker 写日志失败

![Docker Desktop 因无法写入日志而报磁盘空间不足](/assets/agent-disk-incident/docker-no-space.png)

弹窗中的关键错误是：

```text
write ~/Library/Containers/com.docker.docker/Data/log/vm/init.log:
no space left on device
```

Docker 日志记录的错误时间是 **15:51（日本时间，UTC+9）**。检查磁盘时，内置盘 Data 卷显示已用 188 GiB、可用仅 1.7 GiB，使用率显示 100%。这里的可用空间和使用率来自当时的 `df` 输出；即使显示尚有少量空间，也已经出现写入失败。

与此同时，Docker 的 `Docker.raw` 指向外置盘 `/Volumes/AiCode/docker/engine/Docker.raw`。当时外置盘有约 822 GiB 可用，虚拟磁盘实际占用约 24 GiB。因此，不能只看 Docker 数据盘所在位置：**Docker Desktop 的日志和应用本身仍在 Mac 内置盘上。**

## 二、内置盘的空间去了哪里

Claude Code 的“本地 Docker 故障排查”记录中，故障附近检查到的主要占用如下。各项来自不同时间的命令输出，**不能简单相加**；父目录与子目录也可能重叠。

| 项目 | 当时观察到的大小 | 说明 |
| --- | ---: | --- |
| Docker 迁移前的旧备份 | 约 14 GiB | 保留在内置盘，当前 `Docker.raw` 已指向外置盘 |
| `~/Backups` 中的 Hermes 备份 | 约 15 GiB | 记录中可见多份约 1.1 GiB 的备份压缩包 |
| Claude Desktop 应用数据 | 约 12 GiB | 包括运行环境等数据，不能一概当作可删除缓存 |
| Codex 应用缓存 | 约 9.9 GiB | 后续检查发现其中包含多份旧更新安装文件 |
| `~/.hermes` | 约 6.9 GiB | Hermes 运行数据 |
| `~/Code` | 约 20 GiB | 本地项目目录，不应当作缓存直接删除 |
| Go 编译缓存 | 约 2.2 GiB | 可以重新构建，但清理后首次编译会变慢 |

一个容易误读的细节是旧 Docker 备份：文件列表显示逻辑大小约 228 GiB，但 `du` 看到实际占用约 14 GiB。这是稀疏文件；评估它占了多少物理空间时，不能直接把显示的逻辑大小当作实际占用。

Hermes 备份每天产生一份、单份约 1.1 GiB，是明确的持续占用线索。不过，当时没有确认备份由哪个调度器触发，也没有核实完整保留策略；不能把它断言为事故的唯一原因。

## 三、恢复：先腾空间，再恢复 Docker

排查记录显示，处理分成两步：

1. 确认当前 Docker 虚拟磁盘的符号链接指向外置盘后，删除内置盘上迁移前的旧备份，并清理 Go 编译缓存。内置盘可用空间从约 1.7 GiB 回升到约 18 GiB。**删除旧备份意味着失去迁移前的回退副本**；确认当前链接存在并不等于验证备份可以随意删除。
2. Docker Desktop 界面仍无法操作。排查发现旧后台进程没有退出，结束残留进程并重启后，引擎恢复响应，记录显示 12 个容器和 27 个镜像仍可见。后续检查时有 10 个容器运行，MySQL 和 Dockge 的健康检查正常。

之后的一次检查显示内置盘可用空间回升到约 37 GiB，`~/Backups` 已不存在。Claude Code 的记录明确表示这一步不是它执行的，也没有确认备份被移动或删除到哪里，因此不能把这部分空间变化归因于某个确定操作。

## 四、根因与边界

**直接故障链路**很清楚：内置盘可用空间耗尽 → Docker Desktop 无法写入内置盘上的日志 → 引擎报错退出。

**容量层面的原因**是长期累计：Agent 的运行环境、缓存和多份备份，与项目、应用数据及迁移遗留备份共同占据了内置盘。没有及时掌握各类数据的增长和保留情况，剩余空间不足以承受后续写入。

**尚未查明的部分**也要保留：没有连续的磁盘占用监控，不能确定最后是谁写满磁盘、哪一项在事故前增长最快，也不能证明所有备份都是 Agent 自动产生的。排查时看到的大文件说明了空间压力，不等于证明它们各自造成了最后一次写入失败。

## 五、后续怎么避免再次发生

1. **监控内置盘的可用空间。** 即使主要项目和 Docker 数据在外置盘，也要关注系统盘；设置阈值提醒，并在空间持续下降时排查增长来源。
2. **给备份设置可核实的保留策略。** 找到实际调度入口和备份位置，确认恢复方式后，再决定保留数量、归档或清理方式。不要在尚未验证备份价值时直接删除。
3. **区分缓存、项目和虚拟机。** 旧安装缓存和可重建编译缓存可以按需检查；Agent 的会话、工作区和虚拟磁盘可能包含需要保留的数据，不能用同一条清理命令处理。
4. **要求 Agent 清理自己的临时产物。** 任务结束后识别本次创建且可重建的临时文件，并报告大体积产物和备份；涉及共享数据、历史会话或镜像时先确认。删除虚拟机内部文件也不一定使宿主机镜像自动缩小，回收方式应以对应应用支持的操作为准。
5. **迁移后清点遗留副本。** 数据迁到外置盘不代表内置盘副本已经消失。确认新位置可用、备份和回退需求后，再处理旧副本。

这次排查最有价值的发现是：**存储位置和故障位置不一定相同**。Docker 的大文件在外置盘，仍依赖内置盘写入日志；多个工具各自留下的文件也许都合理，但累积起来会共同耗尽同一块系统盘。
