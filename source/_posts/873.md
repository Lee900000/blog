MySQL 迁移 PostgreSQL，真正麻烦的地方通常不是 CRUD 语法。

而是迁移之后发现：

```text
连接突然满了
SQL 超时了
索引不走了
事务卡死了
程序断线了
自增 ID 冲突了
同样 SQL 跑得比 MySQL 慢
UPDATE 越跑表越大
```

所以这篇文章不从数据库理论开始，而是直接按**线上常见问题**横向对比。

# 二、问题 1：连接数突然打满

## MySQL

以前可能是：

```text
10 个服务
每个服务 100 个连接

= 1000 Connections
```

MySQL：

```ini
max_connections = 1500
```

还能继续跑。

* * *

## PostgreSQL

如果直接迁移：

```text
10 个服务
×
100 Connections
=
1000 PostgreSQL Connections
```

就可能出现：

```text
too many clients already
```

或者数据库 CPU / 内存明显上升。

原因之一是 PostgreSQL 的连接模型与 MySQL 不完全相同。

### 错误迁移方式

```text
MySQL

max_connections = 2000

↓

PostgreSQL

max_connections = 2000
```

这不是解决方案。

### 更合理

```text
Application
     │
     ↓
 Go Connection Pool
     │
     ↓
   PgBouncer
     │
     ↓
 PostgreSQL
```

例如 Go：

```go
db.SetMaxOpenConns(50)
db.SetMaxIdleConns(20)
db.SetConnMaxLifetime(time.Hour)
db.SetConnMaxIdleTime(10 * time.Minute)
```

### 核心区别

```text
MySQL 思路：

连接不够
   ↓
max_connections 调大


PostgreSQL 思路：

连接不够
   ↓
先检查连接池
   ↓
检查服务实例数量
   ↓
检查慢 SQL / 长事务
   ↓
必要时 PgBouncer
```

# 三、问题 2：SQL Timeout，但 SQL 明明有索引

例如：

```sql
UPDATE account
SET balance = balance - 100
WHERE user_id = 10001;
```

正常执行：

```text
0.3 ms
```

线上却：

```text
30 seconds timeout
```

很多人的第一反应：

```text
SQL 慢
 ↓
是不是没索引？
```

但真正情况可能是：

```text
Transaction A

UPDATE account
WHERE user_id = 10001;

        │
        ↓
   持有 Row Lock
        │
        │
        ▼

Transaction B

UPDATE account
WHERE user_id = 10001;

        │
        ↓
    等待 30 秒
        │
        ↓
      Timeout
```

实际：

```text
SQL执行：0.3ms

等待锁：29999ms
```

所以：

> Timeout ≠ SQL慢。

# 四、MySQL / PostgreSQL Timeout 对照

```text
                    一次数据库请求
                           │
                           ▼
                     获取连接池
                           │
                 Pool Wait Timeout
                           │
                           ▼
                     建立连接
                           │
                   Connect Timeout
                           │
                           ▼
                       执行 SQL
                     /           \
                    /             \
             Lock Timeout   Statement Timeout
```

对应：

<table><thead><tr><th>类型</th><th>MySQL</th><th>PostgreSQL</th></tr></thead><tbody><tr><td>建立连接</td><td>connect timeout</td><td>connect timeout</td></tr><tr><td>SQL执行</td><td><code>max_execution_time</code></td><td><code>statement_timeout</code></td></tr><tr><td>锁等待</td><td><code>innodb_lock_wait_timeout</code></td><td><code>lock_timeout</code></td></tr><tr><td>空闲连接</td><td><code>wait_timeout</code></td><td><code>idle_session_timeout</code></td></tr><tr><td>空闲事务</td><td>无完全对应</td><td><code>idle_in_transaction_session_timeout</code></td></tr></tbody></table>

排查 Timeout 时不要直接：

```text
Timeout
 ↓
加索引
```

应该：

```text
Timeout
 │
 ├─ 没拿到连接？
 │
 ├─ 建连接失败？
 │
 ├─ 在等锁？
 │
 ├─ SQL 真慢？
 │
 └─ 网络问题？
```

# 五、问题 3：断线重连

## MySQL 常见

```text
MySQL server has gone away
```

```text
Lost connection to MySQL server
```

* * *

## PostgreSQL 常见

```text
server closed the connection unexpectedly
```

```text
connection reset by peer
```

```text
broken pipe
```

* * *

两边本质类似：

```text
连接建立
   │
   ↓
放入连接池
   │
   ↓
长时间未使用
   │
   ↓
DB / Proxy / Network
将连接断开
   │
   ↓
Application 再次拿到
   │
   ↓
发现连接已失效
```

正确方式：

```text
Connection Pool

 ├─ Connection A √
 ├─ Connection B √
 ├─ Connection C ×
 │        │
 │        ↓
 │     Destroy
 │        │
 │        ↓
 │   New Connection
 │
 └─ Connection D √
```

不要在业务代码里永久保存：

```go
conn := db.Conn(...)
```

然后无限使用。

# 六、问题 4：同一条 SQL，MySQL 能跑，PostgreSQL 报错

这是迁移时最直观的问题。

MySQL：

```sql
SELECT *
FROM users
WHERE id = '10001';
```

假设：

```text
id = BIGINT
```

MySQL 很多情况下会自动转换：

```text
'10001'
   ↓
10001
```

然后执行。

PostgreSQL 更严格。

可能出现：

```text
operator does not exist:
bigint = character varying
```

也就是：

```text
BIGINT
  =
VARCHAR

×
```

# 七、最危险的“临时修复”：CAST

开发看到报错以后，很容易：

```sql
WHERE user_id::text = '10001'
```

SQL 可以跑了。

但是问题来了。

原来：

```text
user_id
   │
   ↓
BTree Index
   │
   ↓
Index Scan
```

改成：

```text
user_id::text
     │
     ↓
Function / Cast
     │
     ↓
可能无法使用原索引
     │
     ↓
Seq Scan
```

正确方式应该是：

```sql
WHERE user_id = 10001
```

即：

```text
错误做法：

Column → CAST


正确做法：

Parameter → 正确的数据类型
```

这点在 Go 项目里尤其重要。

# 八、问题 5：事务里一个 SQL 报错，后面全部执行不了

这是 PostgreSQL 和 MySQL 使用体验差异中非常重要的一点。

例如：

```sql
BEGIN;

INSERT INTO users(id)
VALUES(1);
```

发生唯一键冲突：

```text
duplicate key value violates unique constraint
```

代码觉得：

```text
没事
catch(error)
继续
```

然后：

```sql
UPDATE users
SET name = 'karp'
WHERE id = 1;
```

PostgreSQL：

```text
current transaction is aborted,
commands ignored until end of transaction block
```

实际事务状态：

```text
BEGIN
  │
  ▼
SQL 1
  │
  ▼
ERROR
  │
  ▼
Transaction = ABORTED
  │
  ├──── SQL 2 ×
  ├──── SQL 3 ×
  ├──── SQL 4 ×
  │
  ▼
ROLLBACK
```

所以 PostgreSQL：

```text
事务 SQL 报错
     ↓
不要继续
     ↓
ROLLBACK
```

如果业务确实需要局部失败：

```text
SAVEPOINT
```

# 九、问题 6：死锁

MySQL：

```text
Deadlock found when trying to get lock
```

PostgreSQL：

```text
deadlock detected
```

典型：

```text
Transaction A             Transaction B

Lock User 1001            Lock User 1002
      │                          │
      ▼                          ▼
Lock User 1002            Lock User 1001
      │                          │
      └─────────┐      ┌─────────┘
                ▼      ▼
                 Deadlock
```

错误解决方式：

```text
Deadlock
   ↓
把 Timeout 从 5 秒改成 30 秒
```

没有意义。

因为：

```text
A 等 B

B 等 A
```

等 30 秒还是死锁。

正确解决：

```text
统一加锁顺序
```

例如：

```text
永远按照：

user_id ASC
```

所以两个事务都：

```text
1001
 ↓
1002
 ↓
1003
```

同时应用层：

```text
Deadlock
    │
    ↓
Rollback
    │
    ↓
Retry
```

# 十、问题 7：索引明明存在，为什么 PostgreSQL 不走？

例如：

```sql
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

SQL：

```sql
SELECT *
FROM orders
WHERE user_id = 10001;
```

可能：

```text
Index Scan
```

但改成：

```sql
WHERE user_id::text = '10001'
```

可能：

```text
Seq Scan
```

另外：

```sql
WHERE DATE(created_at) = '2026-08-13'
```

也可能影响索引。

建议：

```sql
WHERE created_at >= '2026-08-13 00:00:00'
AND created_at < '2026-08-14 00:00:00'
```

# 十一、不要认为 Seq Scan 一定不好

例如：

```text
orders

总记录数：1000万

查询结果：800万
```

这种情况下：

```text
Index Scan
```

不一定比：

```text
Seq Scan
```

快。

所以迁移 PostgreSQL 后不要：

```text
看到 Seq Scan
    ↓
强制加索引
```

而应该：

```text
EXPLAIN ANALYZE
       │
       ├── actual time
       ├── rows
       ├── loops
       ├── cost
       └── Scan Type
```

# 十二、问题 8：MySQL 的联合索引照搬后，PG 为什么性能不一样？

MySQL 原来：

```sql
INDEX idx_user_status_time(
    user_id,
    status,
    created_at
)
```

SQL：

```sql
SELECT *
FROM orders
WHERE user_id = 10001
AND status = 1
ORDER BY created_at DESC
LIMIT 20;
```

MySQL：

```text
运行很好
```

迁移 PostgreSQL 后：

```text
SQL能跑
```

不代表：

```text
执行计划一样
```

因为：

```text
MySQL Optimizer
      ≠
PostgreSQL Optimizer
```

所以迁移应该：

```text
旧 MySQL SQL
    │
    ↓
EXPLAIN
    │
    ↓
记录计划


PG SQL
    │
    ↓
EXPLAIN ANALYZE
    │
    ↓
重新验证
```

不是：

```text
DDL复制完成
=
索引迁移完成
```

# 十三、问题 9：UPDATE 越多，PostgreSQL 表为什么越来越大？

这是 PostgreSQL 和 MySQL 非常核心的差异。

MySQL InnoDB 可以简单理解：

```text
Current Row
    │
    ↓
 Undo Log
    │
    ↓
Old Version
```

PostgreSQL：

```text
Tuple V1

UPDATE
   │
   ▼

Tuple V1 → Old / Dead
Tuple V2 → New
```

再次 UPDATE：

```text
Tuple V1 → Dead
Tuple V2 → Dead
Tuple V3 → Current
```

所以：

```text
UPDATE
UPDATE
UPDATE
UPDATE
UPDATE
```

可能产生大量：

```text
Dead Tuple
```

* * *

# 十四、这就是为什么 PostgreSQL 必须理解 VACUUM

PostgreSQL：

```text
UPDATE / DELETE
       │
       ▼
Dead Tuple
       │
       ▼
Autovacuum
       │
       ▼
清理 / 标记可复用空间
```

如果 Autovacuum 跟不上：

```text
大量 UPDATE
      │
      ▼
大量 Dead Tuple
      │
      ▼
Table Bloat
      │
      ▼
表越来越大
      │
      ▼
扫描越来越慢
      │
      ▼
IO越来越高
```

例如：

```text
有效业务数据：

10 GB

实际表空间：

50 GB
```

这种问题在 PostgreSQL 中并不罕见。

最典型：

```text
订单表
 │
 ├─ pending
 ├─ matching
 ├─ filled
 ├─ canceled
 └─ settled
```

一个订单不断：

```text
UPDATE status
UPDATE filled_qty
UPDATE avg_price
UPDATE fee
UPDATE time
```

以及：

```text
资产
持仓
任务状态
队列任务

```

都是高频 UPDATE 场景。

所以交易系统迁移 PostgreSQL 时：

> Autovacuum 不是 DBA 才需要知道的东西，核心开发也必须理解。

# 十六、问题 10：一个没提交的事务为什么能把数据库拖慢？

例如：

```sql
BEGIN;
```

执行一些 SQL。

然后程序因为 Bug：

```text
忘记 Commit
忘记 Rollback
```

连接变成：

```text
idle in transaction
```

PG 中：

```text
Long Transaction
      │
      ▼
Old Snapshot
      │
      ▼
旧 Tuple 不能正常回收
      │
      ▼
Vacuum 受影响
      │
      ▼
Dead Tuple 增长
      │
      ▼
Table Bloat
```

所以 MySQL 迁移 PostgreSQL 后：

```text
连接监控
```

不能只看：

```text
active connection
```

还要重点看：

```text
idle in transaction
```

# 十七、问题 11：导完数据后，自增 ID 冲突

MySQL：

```sql
AUTO_INCREMENT
```

比如：

```text
当前最大 ID：

100000
```

下一条：

```text
100001
```

PostgreSQL 常用：

```text
Identity / Sequence
```

迁移数据时如果只是：

```text
COPY data
```

导入：

```text
1
2
3
...
100000
```

但是 Sequence 仍然：

```text
1
```

下一条 INSERT：

```text
id = 1
```

然后：

```text
duplicate key
```

所以迁移完成必须验证：

```text
MAX(id)

        VS

Sequence Current Value
```

必须保证：

```text
Sequence >= MAX(id)
```

# 十八、问题 12：UPSERT 直接不能用了

MySQL：

```sql
INSERT INTO balance(user_id, amount)
VALUES(10001, 100)
ON DUPLICATE KEY UPDATE
amount = VALUES(amount);
```

PostgreSQL：

```sql
INSERT INTO balance(user_id, amount)
VALUES(10001, 100)
ON CONFLICT(user_id)
DO UPDATE SET
amount = EXCLUDED.amount;
```

迁移项目中可以直接全局搜索：

```text
ON DUPLICATE KEY UPDATE
```

全部需要处理。

# 十九、问题 13：LIMIT 写法不同

MySQL：

```sql
LIMIT 100, 20
```

意思：

```text
OFFSET = 100
LIMIT  = 20
```

PostgreSQL：

```sql
LIMIT 20 OFFSET 100
```

所以：

```text
MySQL

LIMIT offset,size

        ↓

PostgreSQL

LIMIT size OFFSET offset
```

# 二十、问题 14：大 OFFSET 两边都会慢

例如：

```sql
SELECT *
FROM trade
ORDER BY id DESC
LIMIT 100 OFFSET 5000000;
```

数据库实际上：

```text
读取前面大量数据
      │
      ▼
丢掉 5000000 条
      │
      ▼
返回 100 条
```

更好的方式：

```sql
SELECT *
FROM trade
WHERE id < 90000000
ORDER BY id DESC
LIMIT 100;
```

也就是：

```text
OFFSET Pagination

       ↓

Keyset Pagination
```

对于：

```text
订单
成交
资金流水
账单
历史记录
```

尤其重要。

# 二十一、问题 15：MySQL 的 tinyint(1) 到 PG 怎么处理？

MySQL：

```sql
is_deleted TINYINT(1)
```

常见：

```text
0 = false
1 = true
```

PostgreSQL：

```sql
is_deleted BOOLEAN
```

直接：

```text
TRUE
FALSE
```

但不要把所有：

```text
tinyint
```

都改成：

```text
boolean
```

例如：

```text
status = 0 Pending
status = 1 Success
status = 2 Failed
```

这种应该：

```text
SMALLINT
```

而不是 BOOLEAN。

# 二十二、问题 16：JSON 应该迁成 JSON 还是 JSONB？

MySQL：

```text
JSON
```

PostgreSQL：

```text
JSON
JSONB
```

如果 JSON 只是：

```text
保存
读取
```

JSON 可以。

但如果需要：

```text
WHERE 查询
包含判断
索引
字段过滤
```

通常应该重点考虑：

```text
JSONB
```

例如：

```sql
SELECT *
FROM orders
WHERE extra @> '{"symbol":"BTCUSDT"}';
```

再结合：

```text
GIN Index
```

所以：

```text
MySQL JSON
```

不要机械：

```text
↓
PG JSON
```

应该：

```text
MySQL JSON
     │
     ├─ 只是保存 → JSON
     │
     └─ 需要查询 → JSONB
```

# 二十三、问题 17：时间字段最容易出现“数据没错，但业务错了”

MySQL 常见：

```text
DATETIME
TIMESTAMP
```

PostgreSQL：

```text
timestamp
timestamptz
```

迁移时必须确认：

```text
Application
     │
     ├─ UTC ?
     ├─ Asia/Shanghai ?
     └─ Asia/Tokyo ?

Database
     │
     └─ TimeZone ?

Server
     │
     └─ TimeZone ?
```

否则可能出现：

```text
数据库：

2026-08-13 08:00

应用理解：

UTC

实际业务：

UTC+8
```

结果差：

```text
8 Hours
```

交易系统建议：

```text
数据库内部

UTC
```

展示：

```text
UTC
 │
 ├─ Asia/Shanghai
 └─ Asia/Tokyo
```

# 二十四、问题 18：Go 代码不能只换 Driver

MySQL：

```go
db.Query(
    "SELECT * FROM users WHERE id = ?",
    id,
)
```

PostgreSQL：

```go
db.Query(
    "SELECT * FROM users WHERE id = $1",
    id,
)
```

也就是：

```text
MySQL

?


PostgreSQL

$1
$2
$3
```

如果项目有几千条手写 SQL：

```text
Driver 替换
```

只是整个迁移的一小部分。

# 二十九、最后浓缩成一句话

MySQL 迁移 PostgreSQL：

```text
不是

MySQL SQL
   ↓
改一下语法
   ↓
PostgreSQL


而是


MySQL System
      │
      ├─ SQL
      ├─ Data Type
      ├─ Index
      ├─ Transaction
      ├─ Connection Pool
      ├─ Retry
      ├─ Timeout
      └─ Operation Model
              │
              ▼
       PostgreSQL System
```

真正最容易踩坑的可以归纳成：

```text
① 类型更严格

② 事务出错后必须 Rollback

③ 不要照搬 MySQL 连接数

④ Timeout 要区分 SQL / Lock / Connection

⑤ 不要为了兼容到处 CAST

⑥ 索引必须重新 EXPLAIN ANALYZE

⑦ UPDATE / DELETE 要理解 Dead Tuple

⑧ PostgreSQL 必须理解 VACUUM

⑨ 必须监控 Long Transaction

⑩ 必须监控 idle in transaction

⑪ 数据迁移后检查 Sequence

⑫ Deadlock / Serialization Failure 要 Retry

⑬ SQL 能执行 ≠ 性能没问题

⑭ Schema 迁完 ≠ 数据库迁移完成
```

如果原系统属于：

```text
交易所
支付
订单
账户
资金
持仓
清算
账务
```

那么还需要把下面几项提高到最高优先级：

```text
NUMERIC 精度
     +
事务一致性
     +
行锁竞争
     +
Deadlock Retry
     +
长事务
     +
Connection Pool
     +
Autovacuum
     +
Table Bloat
```

这些才是 MySQL → PostgreSQL 迁移完成后，最容易在线上真正出问题的地方。
